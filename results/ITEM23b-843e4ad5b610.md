## Verdict

- **Correctness gate passed:** speed has 0 errors on S3 small queries at 32 clients in all 3 rounds (and 0 at every
  other step, S3 and local); the ITEM 23 failure is fixed.
- **Gains:** concurrent small-query p50 at 8/32 clients halved on S3 (0.50-0.52) and 37-45 % lower locally; local
  c32 throughput ~+30 %; closed-loop load +9-22 % at 8-128 clients, within 4-6 % of upstream native at 128 clients;
  peak RSS under load 823 MB vs 4432 balanced and 4928 upstream (0.17-0.19). The ITEM 23 local c1 p50 penalty
  (1.06 / 1.13) is gone (0.98 / 0.97).
- **Remaining cost: S3 tail latency.** With 8 and 32 concurrent S3 clients, p95 is 1.33-1.54x balanced in every round
  (c32 p95 ~26 s vs ~17-18 s; c8 p95 ~7.2 s vs ~5.3-5.4 s; JDBC p99 1.37-1.40), and total wall time for the 1280 S3
  queries at 32 clients is 5-15 % longer. So on S3 the speed profile trades a halved median for longer tails and no
  throughput gain. This was 1.42-1.44 at c8 in ITEM 23, so it is unchanged in kind. Local ADBC c8 p95 1.13 (1.09-1.16)
  is also unchanged from ITEM 23 (1.15).
- **Next for item 23:** if the speed profile should be the default on S3, look at the S3 tail at 8/32 clients
  (the per-query latency samples are in the run artifact `ab-i23b-small-s3`, B/r*/small-*8* and *32*). Speed can be
  used on local disk and for closed-loop load as it is.
